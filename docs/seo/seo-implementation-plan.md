## 1. الهدف

رفع الظهور العضوي لموقع عالم الستائر في الكويت للكلمات ذات النية التجارية، وتحسين جودة الزيارات والتحويل إلى استفسارات فعلية. الأولويات الأساسية:

1. تركيب الستائر وفني تركيب الستائر.
2. تفصيل الستائر.
3. الأنواع التي يقدمها النشاط فعلًا، خصوصًا الويفي والرول والبلاك أوت.
4. الأسعار وطلب عرض سعر.
5. البحث المحلي في مناطق الكويت، بشرط تقديم الخدمة فعليًا ووجود محتوى محلي مفيد.
6. الكلمات الإنجليزية ذات الصلة بخدمات النشاط، دون ترجمة آلية ضعيفة.

لا توجد ضمانات لترتيب معين أو موعد محدد للظهور. يجب قياس النتائج باستخدام Search Console وبيانات التحويلات الفعلية.

## 2. تعليمات إلزامية للمنفذ (Claude)

### 2.1 نطاق العمل والصلاحيات
- اعمل حصريًا على المستودع `stayerkw/stayerkw.github.io` والنطاق `alamcurtainskw.com`.
- لا تفتح ولا تعدّل ولا تنشئ ملفات في أي مستودع آخر.
- لا تغيّر إعدادات GitHub أو النطاق أو DNS أو الأسرار أو صلاحيات الحساب.
- لا تنشر مباشرة على `main` ولا تنفذ نشرًا إنتاجيًا مباشرًا.
- أنشئ فرع عمل مستقلًا، ثم افتح Pull Request للمراجعة. إذا لم تتوفر صلاحية إنشاء فرع/PR، سلّم الملفات والتغييرات المقترحة دون محاولة تجاوز الصلاحيات.
- لا تحذف أو تعِد تسمية مسارات قائمة، ولا تضف Redirects، ولا تدمج صفحات، قبل توثيق سبب واضح وفحص الفهرسة وSearch Console والروابط الداخلية والخارجية وcanonical.
- لا تنفذ تغييرات كبيرة غير قابلة للعكس. كل تغيير يجب أن يكون محدودًا، موثقًا، وقابلًا للمراجعة والتراجع.
- لا تضف خدمات أو أنواع ستائر أو مناطق تغطية أو عناوين فروع أو أسعارًا أو ضمانات أو أرقام خبرة أو شهادات أو تقييمات من عندك.
- عند غياب معلومة تجارية، اتركها كما هي أو ضع سؤالًا واضحًا لصاحب الموقع بدل اختلاقها.
- لا تستخدم حشو الكلمات المفتاحية أو صفحات المدن المتشابهة أو نصوصًا مولدة متكررة على نطاق واسع.
- لا تنشئ روابط خلفية مدفوعة/مصطنعة أو مراجعات مزيفة أو بيانات منظمة مضللة.
- لا تغيّر الهوية البصرية أو تصميم الموقع إلا إذا كان ذلك ضروريًا لمهمة SEO ومحدود الأثر، مع الحفاظ على تجربة المستخدم الحالية.
- حافظ على العربية الطبيعية واتجاه RTL، وعلى الإنجليزية في صفحاتها المخصصة.
- لا تُظهر بيانات خاصة أو مفاتيح API أو أرقام حسابات في ملفات عامة أو مخرجات PR.

### 2.2 التوثيق المستمر وتحديث ملف الخطة — إلزامي بعد كل مهمة
هذا شرط أساسي وليس خيارًا:
- بعد إنجاز **كل مهمة أو مجموعة تغييرات مترابطة** من هذه الخطة، حدّث ملف الخطة نفسه قبل اعتبار المهمة مكتملة.
- احتفظ بملف الخطة داخل المستودع في مسار توثيق واضح، مثل `docs/seo/seo-implementation-plan.md`، أو حدّث الملف الموجود إذا كان قد أُنشئ بالفعل. لا تنشئ نسخًا متكررة بلا داعٍ.
- لا تستبدل الخطة الأصلية بملاحظات مختصرة. احتفظ بالأهداف والخطة الكاملة، وأضف سجل تنفيذ مؤرخًا.
- حدّث أيضًا نسخة قابلة للتسليم للمستخدم بصيغتي Markdown وDOCX بعد كل مرحلة تنفيذية رئيسية، أو بعد كل مهمة إذا كان حجم العمل صغيرًا.
- في نهاية كل مهمة، سلّم للمستخدم **ملف الخطة المحدث** مع رابط تنزيل، حتى يستطيع معرفة ما تم إنجازه وما بقي. لا تنتظر نهاية الخطة كاملة.
- لا تكتفِ بقول «تم». أرفق الملف المحدث وملخصًا موجزًا للتغييرات.
- إذا لم تستطع كتابة الملفات أو إنشاء مرفقات بسبب الصلاحيات، اذكر ذلك صراحة وسلّم المحتوى المحدث كاملًا دون الادعاء أنك حدّثت الملف.
- لا تسجل المهمة على أنها مكتملة إذا لم تنفذها أو لم تتحقق من نتائجها.

### 2.3 شرح كل تعديل: السبب والدليل والمصدر
لكل تغيير في الكود أو المحتوى أو SEO، أضف في سجل الخطة جدولًا يحتوي على:
1. **المهمة/الملف/المسار المتأثر.**
2. **الحالة:** لم يبدأ / قيد التنفيذ / مكتمل / متوقف بانتظار معلومة أو موافقة.
3. **التغيير قبل وبعد:** وصف دقيق أو مقتطف مناسب.
4. **سبب التغيير:** المشكلة أو فرصة التحسين التي يعالجها.
5. **الأساس الذي استند إليه:** بيانات GSC، أو ملف أحجام البحث، أو فحص تقني، أو أفضل ممارسة موثقة، أو دليل من المنافسين.
6. **الأرقام كاملة مع تعريفها:** الفترة الزمنية، البلد/الفلتر، نوع القياس، والعينة عند توفرها. ميّز بين مرات الظهور والنقرات وحجم البحث الشهري ومتوسط الموضع.
7. **مصدر كل رقم أو ادعاء:** اسم التقرير أو الأداة، رابط/مسار الملف أو اسم التقرير، تاريخ الاستخراج، والفلاتر المستخدمة. إذا لم يوجد مصدر موثوق، اكتب «لا يوجد قياس مباشر» ولا تخترع رقمًا.
8. **النتيجة المتوقعة وحدود اليقين:** اشرح المنطق دون ضمان ترتيب أو نسبة نمو.
9. **الاختبارات التي أُجريت ونتيجتها الفعلية:** build، lint، schema validation، الروابط، HTML النهائي، أو غيرها.
10. **المخاطر وخطة التراجع** إذا كان التغيير يؤثر على المسارات أو canonical أو إعادة التوجيه أو بنية البيانات.
- فرّق بوضوح بين **البيانات المرصودة** و**الاستنتاج** و**التوصية**.
- لا تنسب تحسنًا إلى تعديل لم تُقَس نتائجه بعد.
- لا تستخدم أرقامًا تقديرية على أنها أرقام فعلية، ولا تنقل أرقامًا من بلد أو فترة مختلفة دون تصريح واضح.
- أرفق مراجع قابلة للتحقق، ويفضل روابط التقارير أو مسارات الملفات ومراجع الوثائق الرسمية عند الاستناد إلى أفضل ممارسة.
- عند استخدام بيانات المنافسين، اذكر عنوان الصفحة وتاريخ الفحص وما أمكن التحقق منه؛ لا تفترض أن عنصرًا معينًا هو سبب ترتيب المنافس دون دليل.

### 2.4 تسلسل التنفيذ
1. افحص الفرع الحالي وحالة المستودع والبناء قبل التغيير.
2. أنشئ تقريرًا أساسيًا للصفحات والروابط والـSEO الفني قبل التعديل.
3. اقرأ الملفات ذات الصلة كاملة قبل تعديلها.
4. جهّز خريطة كلمات إلى صفحات، ولا تنشئ صفحة قبل التأكد من عدم وجود صفحة مناسبة.
5. نفّذ التغييرات على دفعات صغيرة.
6. شغّل أوامر الاختبار والبناء وSEO lint المتاحة في المشروع.
7. افحص HTML الناتج والـcanonical والعناوين والـSchema والروابط.
8. راجع الفرق `diff` للتأكد من عدم وجود تغييرات غير مطلوبة.
9. حدّث الخطة وسجل التنفيذ حسب البنود أعلاه.
10. افتح PR يتضمن ملخصًا، وقائمة الملفات، وسبب كل تغيير، ونتائج الاختبارات، وأي نقاط تحتاج موافقة صاحب الموقع.
11. لا تدمج PR ولا تنشره للإنتاج دون موافقة صريحة.

### 3.2 ضوابط تفسير البيانات
- هذه أرقام المصدر، وليست ضمانًا للزيارات أو الطلبات.
- لا تجمع الصيغ الإملائية التي أشار المصدر إلى دمجها.
- «غير متاح» لا تعني صفر بحث؛ لا تحوّلها إلى صفر.
- لا تستنتج أن الكلمات ذات حجم أقل غير مفيدة؛ قيّم نية البحث والقيمة التجارية والملاءمة.
- إذا كانت KD «غير متاح»، لا تخترع صعوبة SEO. مؤشر المنافسة الإعلانية ليس صعوبة SEO العضوية.
- لا تستخدم أحجام بحث خارج الكويت كبديل.
- لا تضع أحجام البحث داخل محتوى الموقع؛ هي بيانات تخطيط داخلية.
- احتفظ بالمصدر وتاريخ الاستخراج والفلاتر في سجل الخطة.
- أي رقم لا يمكن التحقق منه يجب وسمه بوضوح: «غير متحقق» أو «لا يوجد قياس مباشر».

### 3.3 بيانات Search Console
- استخدم الفترة والفلتر المحددين في كل تقرير، ولا تخلط بيانات آخر 28 يومًا مع ثلاثة أشهر.
- افصل بين بيانات الموقع ككل وبيانات الكويت فقط.
- سجّل تاريخ استخراج التقرير والفترة الزمنية والبلد ونوع البحث والصفحات/الاستعلامات المشمولة.
- مرات الظهور والنقرات في GSC ليست حجم البحث في السوق.
- متوسط الموضع ليس ترتيبًا ثابتًا لكل مستخدم أو جهاز أو موقع.
- إذا تعذر الوصول إلى تقرير، لا تدّعِ أنك راجعته؛ وثّق الحاجة إليه.
- بما أن الموقع حديث، فسّر النتائج بحذر ولا تقارنها مباشرة بمواقع قديمة أو بفترات غير متكافئة.

## 5. أولويات التنفيذ

### P0 — الفحص والسلامة الفنية
1. توثيق الوضع الحالي للصفحات الأساسية قبل أي تعديل.
2. فحص `robots.txt` وsitemap وHTTP status وcanonical والفهرسة.
3. فحص Titles وmeta descriptions وH1 وBreadcrumbs والروابط الداخلية.
4. مراجعة مكوّن Schema الحالي ومنع التكرار أو التعارض.
5. تشغيل build وSEO lint والاختبارات المتاحة.
6. مراجعة مسارات الويفي والرول المتقاربة دون حذف أو تحويل فوري.

### P1 — صفحات التحويل الرئيسية
1. صفحة تركيب الستائر.
2. صفحة تفصيل الستائر.
3. الصفحة الرئيسية.
4. صفحة الويفي.
5. صفحة الرول.
6. صفحة البلاك أوت.
7. صفحة الأسعار.

حسّن الصفحات الحالية أولًا بدل إنشاء نسخ جديدة. اجعل كل صفحة تجيب بوضوح عن نية الباحث وتحتوي معلومات حقيقية وصورًا مناسبة وCTA واضحًا.

### P2 — توسيع مضبوط
1. صفحات أنواع إضافية يقدمها النشاط فعلًا.
2. تحسين الصفحات الإنجليزية ذات القيمة.
3. صفحات مناطق مختارة عند وجود سبب حقيقي.
4. محتوى إرشادي يدعم الصفحات التجارية ويربط إليها داخليًا.
5. تتبع نقرات WhatsApp والهاتف إن كانت البنية التحليلية متاحة.

## 6. متطلبات صفحات الخدمات والأنواع

كل صفحة مهمة يجب أن تتضمن، بحسب ملاءمتها:
- Title فريد يصف الخدمة والموقع دون حشو.
- Meta description واضحة وغير مضللة.
- H1 واحد واضح ومتسق مع موضوع الصفحة.
- مقدمة مفيدة ومحددة، لا فقرة عامة مكررة.
- تفاصيل صحيحة عن الخدمة أو النوع.
- صور أصلية أو صور مصرح باستخدامها، مع ضغط وأبعاد مناسبين.
- نصوص بديلة تصف الصورة فعلًا.
- روابط داخلية ذات صلة إلى الأسعار والأنواع والخدمات.
- طريقة تواصل واضحة عبر WhatsApp/الهاتف.
- أسئلة شائعة حقيقية يجيب عنها المحتوى، دون ادعاءات غير مؤكدة.
- Breadcrumbs مناسبة إذا كانت مستخدمة في الموقع.
- Canonical صحيح.
- بيانات Schema مناسبة للمحتوى فقط.

لا تفرض عدد كلمات اعتباطيًا. اكتمال الإجابة ودقتها أهم من طول النص. لا تكرر الكلمة المفتاحية بكثافة مصطنعة.

### أمثلة لعناوين يمكن تكييفها بعد فحص الصفحات
- تركيب ستائر في الكويت | فني تركيب ستائر – عالم الستائر
- تفصيل ستائر في الكويت حسب الطلب | عالم الستائر
- ستائر ويفي في الكويت | الأنواع والتفصيل
- ستائر رول في الكويت | الخيارات وطلب عرض سعر
- أسعار الستائر في الكويت | تفاصيل الأسعار وطلب عرض سعر

هذه أمثلة وليست نصوصًا يجب تطبيقها آليًا. عدّلها بناءً على المحتوى الفعلي وتجنب التكرار بين الصفحات.

## 7. قواعد المحتوى المحلي

- لا تدّعِ وجود فرع في منطقة إذا لم يكن هناك فرع حقيقي.
- يجوز وصف نطاق الخدمة فقط إذا كان النشاط يخدم المنطقة بالفعل.
- لا تنشئ صفحات لكل منطقة باستبدال اسم المنطقة في نص ثابت.
- الصفحة المحلية تستحق الإنشاء إذا كانت تلبي حاجة فعلية بمعلومات فريدة قابلة للتحقق.
- لا تنشئ Google Business Profiles متعددة لنفس النشاط أو مواقع افتراضية.
- حافظ على اتساق اسم النشاط ورقم الهاتف وساعات العمل والعنوان المنشور.
- لا تضف مراجعات أو تقييمات أو شهادات عملاء غير حقيقية.

## 8. Schema والبيانات المنظمة

- راجع `src/components/Schema.astro` والصفحات التي تستدعيه قبل التعديل.
- استخدم `LocalBusiness` أو نوعًا أكثر تحديدًا عند ملاءمته، وببيانات حقيقية فقط.
- استخدم `BreadcrumbList` إذا كانت مسارات التنقل ظاهرة ومطابقة.
- استخدم `Product` فقط لمنتجات فعلية تستوفي المتطلبات، لا لصفحات الخدمات.
- استخدم `Article` للمقالات المناسبة.
- لا تعد بظهور نتائج موسعة لمجرد إضافة FAQ Schema.
- تجنب تكرار كيان النشاط أو تضارب الهاتف/الاسم/العنوان بين الصفحات.
- لا تضف تقييمات أو أسعارًا أو عروضًا غير ظاهرة للزائر.
- اختبر JSON-LD من حيث صحة البنية، وراجع الناتج النهائي بعد البناء.

## 9. الصفحات المتقاربة واحتمال التداخل

تحقق خصوصًا من:
- `/curtains/wave/` مقابل `/wave-curtains/`
- `/curtains/roll/` مقابل `/ready-roll-curtains/`

لا تفترض وجود مشكلة من المسارات وحدها. قارن:
- المحتوى والنية.
- مرات الظهور والنقرات والاستعلامات في GSC.
- حالة الفهرسة.
- canonical.
- الروابط الداخلية والخارجية.
- الروابط التي يشير إليها sitemap.

بعد ذلك اقترح أحد الخيارات: الإبقاء والتمييز، أو اختيار صفحة أساسية، أو إعادة توجيه عند وجود مبرر. لا تنفذ الدمج أو إعادة التوجيه قبل الموافقة.

## 10. الأداء وتجربة المستخدم

- قِس LCP وINP وCLS على الصفحات الأساسية.
- لا تضف مكتبات JavaScript كبيرة دون ضرورة.
- حسّن الصور مع الحفاظ على الجودة، وحدد width/height لتقليل CLS.
- راجع الصور الرئيسية و`preload` فقط عندما يكون مبررًا.
- لا تستخدم lazy loading لصورة LCP الرئيسية إذا كان ذلك يؤخر ظهورها؛ استخدمه للصور أسفل الصفحة عند الملاءمة.
- اختبر الهاتف أولًا.
- حافظ على سرعة الوصول إلى واتساب والهاتف دون إزعاج أو تغطية للمحتوى.

## 14. معايير قبول PR

يُقبل PR عندما:
- تكون جميع التغييرات داخل المستودع المحدد وعلى فرع مستقل.
- لا توجد تغييرات غير مقصودة في إعدادات النشر أو النطاق.
- ينجح build وأي اختبارات متاحة، أو يوضح التقرير سبب الفشل الموجود مسبقًا.
- لا توجد أخطاء جديدة في الروابط أو المسارات أو canonical أو sitemap.
- تكون عناوين الصفحات وأوصافها وH1 متسقة وغير مكررة بلا داعٍ.
- لا توجد بيانات تجارية مختلقة.
- Schema صحيحة ولا تحتوي معلومات مضللة أو مكررة.
- يتم فحص التغييرات في diff.
- يتضمن PR ملخصًا لكل ملف تغير ولماذا.
- تتضمن الملاحظات أي قرار يحتاج إلى موافقة صاحب الموقع.
- تم تحديث ملف الخطة وسجل التنفيذ، وتسليم نسخة محدثة للمستخدم.
- لا يتم الدمج أو النشر قبل موافقة صريحة.
